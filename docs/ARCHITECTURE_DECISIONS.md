> 遵循"第一性原理"原则：每个决策从问题本质出发，不因惯例照搬。

## ADR-001: 信号监控优先而非自动交易

**状态**: 已采纳（2026-07-06）
**影响范围**: 全局架构

### 背景
系统默认 `signal_only` 模式，只推送信号不下单。

### 决策
- 默认模式为信号监控 + 绩效验证
- paper/live 模式为可选进阶
- signal_only 模式下跳过 Wisdom LLM 调用，但仍执行硬编码 fallback 获取止损/止盈/仓位建议

### 理由
1. **风险控制**：自动交易需要经过充分验证，信号监控阶段收集实际数据
2. **渐进式验证**：五阶段架构（策略固化→回测→信号监控→模拟盘→实盘）不可跳级
3. **用户自主权**：个人投资者保留最终决策权

### 后续优化
- signal_only 模式卡片添加"仅通知，不构成交易建议"免责声明（v0.6.0）

## ADR-002: 自研轻量引擎而非 qlib

**状态**: 已采纳
**影响范围**: backtest/、analysis/

### 背景
需要回测和绩效分析能力，但 qlib 依赖重（PyTorch、GPU）。

### 决策
自研轻量回测引擎，不引入 qlib 重依赖。

### 理由
1. **依赖轻量**：避免 PyTorch 等重依赖
2. **定制灵活**：A 股特有规则（T+1、涨跌停、手续费）可精确实现
3. **性能足够**：个人使用场景下自研引擎性能满足需求

### 参考
- `src/gugu/backtest/engine.py` — 自研回测引擎
- `src/gugu/analysis/performance.py` — Brinson 归因 + 因子归因

## ADR-003: 三级数据源冗余

**状态**: 已采纳
**影响范围**: data/collectors/

### 背景
免费 API（akshare/东方财富）不稳定，经常被限流或返回空数据。

### 决策
三级数据源冗余 + 自动降级：
- 主源：sina（实时行情）
- 第一降级：akshare（东方财富后端）
- 第二降级：东方财富 push API 直连（httpx）

### 理由
1. **高可用**：单源故障不影响系统运行
2. **免费**：不依赖付费数据源
3. **自动降级**：主源连续失败 3 次后自动并发降级，冷却 5 分钟后切回

### 后续优化
- 资金流 API 不可用时用量价推算 fallback（v0.5.4）
- HTTP 重试 + UA 池轮换防限流（v0.5.4）

## ADR-005: 十大视角评分系统而非单一模型

**状态**: 已采纳（v0.5.0）
**影响范围**: analysis/perspectives/

### 背景
需要多维度评估股票质量，而非单一技术指标或基本面模型。

### 决策
将 10 位投资大师的认知框架量化为独立评分函数（0-10 分），加权汇总。

### 理由
1. **可解释性**：每个评分附带推理链，用户可理解评分依据
2. **模块化**：每个视角独立，可单独启用/禁用/调整权重
3. **木桶效应**：最低分视角决定整体判定，避免单一维度掩盖致命缺陷
4. **无外部依赖**：纯计算函数，无需 LLM 或外部 API

### 架构
```
analysis/perspectives/
├── data_types.py    # StockDataContext, PerspectiveScore, PerspectiveAnalysisResult
├── scorer.py        # 10 个评分函数
├── engine.py        # PerspectiveEngine（单股/批量分析）
└── integrators.py   # 与现有模块的集成桥接
```

### 后续优化
- 技术指标计算缓存（v0.6.0 计划）
- 评分函数单元测试增强（v0.6.0）

## ADR-006: 熔断状态持久化

**状态**: 已采纳（v0.5.0）
**影响范围**: risk/manager.py

### 背景
进程重启后熔断状态丢失，可能绕过 L2 日亏熔断铁律。

### 决策
熔断状态持久化到 `data/risk_state.json`，使用原子写入。

### 理由
1. **铁律不可绕过**：进程重启不应重置熔断状态
2. **原子写入**：防止崩溃导致文件截断
3. **跨日自动失效**：仅恢复当日熔断状态，跨日熔断自动失效

### 权衡
- 文件损坏时保守恢复为非熔断状态（误熔断影响 > 漏熔断）
- 人工可手动删除文件解除熔断（需物理访问服务器）

## ADR-008: 技术指标统一计算

**状态**: 已采纳（v0.6.0）
**影响范围**: analysis/technical.py

### 背景
多个模块（stage_detector、perspectives、alpha_factory）各自实现技术指标计算，存在重复和差异。

### 决策
在 `technical.py` 中集中提供所有常用技术指标计算，各模块通过此模块获取。

### 理由
1. **消除重复**：ATR/RSI/MACD/布林带等指标只需实现一次
2. **一致性**：所有模块使用相同的计算方法，避免结果差异
3. **可测试**：集中测试指标正确性

### 当前指标
- `atr()` — 平均真实波幅
- `sma()` / `ema()` — 移动平均
- `rsi()` — 相对强弱指标（Wilder 平滑）
- `macd()` — 异同移动平均线
- `bollinger()` — 布林带
- `obv()` — 能量潮

## ADR-009: 并发预取与评分

**状态**: 已采纳（v0.6.0）
**影响范围**: engine/main.py、analysis/stock_ranker.py

### 背景
扫描多只股票时串行 I/O 等待导致整体耗时过长。

### 决策
使用 `asyncio.gather` + `Semaphore` 限制并发数，批量预取和评分。

### 理由
1. **I/O 密集型**：数据采集是 I/O 密集型操作，并发可大幅缩短时间
2. **资源控制**：Semaphore 限制并发数，避免过载数据源
3. **异常隔离**：单只股票失败不影响其他股票

### 实现
- `TradingEngine._scan_signals`：批量预取历史数据使用并发
- `StockRanker.rank`：多只股票评分使用并发

## ADR-010: 通知重试指数退避

**状态**: 已采纳（v0.6.0）
**影响范围**: notifier/feishu.py

### 背景
飞书 API 限流时，固定 2 分钟重试可能加剧问题。

### 决策
根据重试次数实现指数退避：第 0 次立即重试，之后每 `2^retry_count` 次触发一次。

### 理由
1. **减少限流**：退避策略降低重试频率，避免触发飞书 QPS 限制
2. **最终送达**：重试次数超限时通过 webhook 发送告警
3. **过期清理**：超过 24 小时的条目自动丢弃（昨日信号今日已无意义）

### 退避策略
| 重试次数 | 触发频率 | 实际间隔 |
|----------|----------|----------|
| 0 | 每次 | ~2min |
| 1 | 每2次 | ~4min |
| 2 | 每4次 | ~8min |
| 3 | 每8次 | ~16min |
| ≥5 | 永久丢弃 | — |

**状态**: 已采纳（v0.6.0）
**影响范围**: config/settings.yaml、scheduler.py

### 背景

- 每个 `add_job` 调用前检查开关
- 修改配置后无需重启（配合 ADR-012 热加载）

## ADR-012: 配置热加载

**状态**: 已采纳（v0.6.0）
**影响范围**: config/__init__.py、scheduler.py

### 背景
修改策略参数或调度配置后需要重启 scheduler，影响盘中交易。

### 决策
提供 `refresh_config()` 和 `config_has_changed()` 接口，scheduler 每 5 分钟检测文件变更自动重载。

### 理由
1. **零停机**：配置修改后无需重启服务
2. **低开销**：基于文件 mtime 比较，无 I/O 开销
3. **安全**：仅刷新配置缓存，不修改运行中的任务（任务变更需下次 setup）

### 实现
- `get_config.cache_clear()` 清除 LRU 缓存
- `config_has_changed()` 比较 `settings.yaml` 的 `st_mtime`
- scheduler 每 5 分钟执行 `_safe_check_config`

- 排序逻辑：视角评分降序 → 涨幅升序

## ADR-015: Walk-Forward 窗口内 PCA 正交化

**状态**: 已采纳（v0.7.0）
**影响范围**: analysis/ml_factor.py

### 背景
MLFactorModel 在因子正交化时对全量数据拟合 PCA，导致 Walk-Forward 训练时用到未来信息（前视偏差），回测结果不可靠。

### 决策
将 PCA 拟合从全量数据改为在 Walk-Forward 窗口内部进行。每个训练窗口独立拟合 PCA，用该窗口的因子协方差矩阵做正交化，仅将拟合好的 PCA 应用于验证集。

### 理由
1. **消除前视偏差**：正交化矩阵只来自训练期因子数据，不泄露验证期信息
2. **适应因子结构变化**： A 股因子间相关性随时间变化，窗口内拟合更准确反映当期因子关系
3. **与 Walk-Forward 一致**：自始就使用 Walk-Forward，只是在正交化步骤遗漏了窗口隔离

### 参考
- `src/gugu/analysis/ml_factor.py` — `_train_single_window()` 方法

## ADR-016: 策略准入门禁与飞书通知联动

**状态**: 已采纳（v0.7.0）
**影响范围**: scripts/validate_strategy_gate.py

### 背景
策略准入门禁验证（`validate_strategy_gate.py`）原本仅输出 CLI 结果，验证通过或失败后用户需要手动查看飞书通知，反馈链路不闭环。

### 决策
新增 `notify_validation()` 和 `format_validation_report()` 函数，验证结果自动推送飞书卡片，新增 `--notify` 命令行选项统一控制。

### 理由
1. **闭环反馈**：验证通过/失败自动飞书推送，用户无需主动查看 CLI 输出

3. **低侵入**：新增 `--notify` 选项，不改变默认 CLI 行为

### 实现
- `notify_validation(result)` — 通过已有 FeishuNotifier 推送验证卡片
- `format_validation_report(result)` — 格式化验证报告为飞书卡片内容
- `--notify` 参数解析后调用通知函数

## ADR-017: Sharpe Ratio 含无风险利率

**状态**: 已采纳（v0.7.0）
**影响范围**: backtest/metrics.py

### 背景
Sharpe Ratio 计算时假设无风险利率为 0，导致低波动市场环境下 Sharpe 值虚高，误导策略比较决策。

### 决策
引入 2% 无风险利率（中国一年期存款利率近似），计算超额收益时减去无风险利率。

### 理由
1. **更准确的收益风险比**：零无风险利率假设在低波动环境下严重高估 Sharpe
2. **行业可比性**：主流量化平台（聚宽、米筐）默认使用 2-3% 无风险利率
3. **A 股市场适配**：2% 接近中国一年期存款基准利率

### 计算
```
Sharpe = (mean_daily_return - risk_free_daily) / std_daily_return * sqrt(252)
risk_free_daily = (1 + 0.02) ** (1/252) - 1
```

## ADR-018: 持仓时间风控基类抽象

**状态**: 已采纳（v0.7.0）
**影响范围**: strategies/base.py、strategies/breakout.py、strategies/ml_factor.py

### 背景
BoxBreakoutStrategy 和 MLFactorStrategy 各自实现 max_hold_days 强制卖出逻辑（30 天未盈利警告/60 天强制清仓），存在代码重复，后续新增策略无法复用。

### 决策
将 max_hold_days 强制卖出逻辑抽取到 `BaseStrategy._check_max_hold_days()` 方法，所有策略继承复用。

### 理由
1. **消除重复**：30 天/60 天规则统一在一处维护
2. **可扩展**：新增策略只需在 settings 中配置 max_hold_days 即可启用
3. **一致性**：所有策略使用相同的持有时间风控标准

### 实现
- `BaseStrategy._check_max_hold_days(positions)` — 检查所有持仓的持有天数
- 30 天未盈利：记录警告，标记减半仓建议
- 60 天未盈利：强制清仓

## ADR-019: 买入准入与绩效结果严格分离

**状态**: 已采纳（2026-07-21）
**影响范围**: engine/signal_pipeline.py、engine/main.py、data/、信号历史与绩效汇总

### 背景

信号通知、订单执行和交易盈利是不同阶段的事实。若把订单成功当作盈利，或把不完整交易纳入平仓胜率，会造成错误反馈；数据不新鲜时进入买入路径，也会让策略验证失去可信度。

### 决策

- 所有买入候选统一经过十大视角门禁；未通过者只能作为研究/通知结果，不能进入买入路径。
- 数据质量只有 `fresh` 允许买入；`stale`、`partial`、`invalid`、`unavailable` 只允许研究/通知。
- `track_live` 和 `signal_only` 只监控和通知，不自动下单；`track_live` 的真实持仓跟踪不改变这一边界。
- 订单成功不等于盈利，绩效分别使用 `execution_success_rate`、`forward_5d_signal_hit_rate`、`closed_trade_win_rate`、`realized_pnl`、`estimated_signal_pnl`。
- 没有完整平仓结果的记录只能用于前向收益追踪，不能进入 `closed_trade_win_rate` 或已实现盈亏统计。

### 理由

1. **第一性原理**：准入资格、执行结果、市场结果分别回答“能不能买”“有没有执行”“最终赚没赚”，不能用一个字段代替。
2. **对抗性审查**：将旧的成功标签拆开，避免成交成功、信号命中或估算收益伪装成已实现盈利。
3. **风险边界**：不新鲜或不完整的数据不得驱动买入，监控模式不产生未经确认的交易副作用。

### 结果

系统保留完整信号历史和通知可见性，同时把可执行买入、研究观察、订单执行和已平仓绩效放在可审计的不同口径中。

## ADR-020: 视觉能力定位 = 验证审计层，不进入策略信号生成

**状态**: 已采纳（2026-08-07）
**影响范围**: 全部策略、rebound-pattern-vision 技能、验证方法论

### 背景

用户问"gugu 中其他策略需要视觉能力吗"。审查了 56 个策略后确认：全部是数值规则驱动（箱体=rolling max/min、双阴=shift 阴阳判断、首板=涨幅阈值、MACD/KDJ/RSI=指标计算），**形态已被确定性代码量化，无前视、可回测、可统计**。

### 决策

- **不给任何策略添加"看图识别"模块**——规则量化已比"AI看图"更精确。
- **视觉能力只用于验证审计层**：发现前视偏差、规则漏洞、教学图互证。
- 判断原则（第一性原理）：**先问"这个形态能被数值规则表达吗？" 能→用规则；不能→才考虑视觉**。gugu 56 个策略全部属于"能"。

### 理由

1. **精确性**：`close > box_high` 比 vision 模型读图判断更精确、可复现。
2. **防前视**：数值规则天然受"信号日可得"约束；视觉特征容易滑入事后特征（见前视偏差教训：视觉评分 V1 用断板后 5 日低点 → 虚高 +5.95%，V2 无前视 → -0.57% 无 alpha）。
3. **成本**：vision API 慢（实测单图超时 600s）且本机未配置视觉模型，不适合实时信号链路。
4. **对抗性审查价值**：视觉分析的真实价值是暴露数据陷阱（断板反包翻案正是视觉特征分析触发的）。

### 适用范围边界

| 用法 | 是否采用 | 说明 |
|------|---------|------|
| 给现有策略加"看图识别" | ❌ | 规则已量化，无增益 |
| 用视觉做形态验证审计 | ✅ | 发现前视偏差/规则漏洞（断板反包已验证） |
| 处理网图/用户截图 | ✅ | 教学互证、快速定位（rebound-pattern-vision） |
| 训练 CNN 看图分类 | ⏸️ | 需 2000+ 跨股样本，等实盘积累 |

### 参考

- `a-stock-quant-backtest` 技能 — 前视偏差翻案完整记录

## ADR-021: 盘中K线隔离修复（P0 前视偏差）

**状态**: 已采纳（2026-08-07）
**影响范围**: engine/engine_mixin.py `_scan_signals`、全部盘中实时信号

### 背景

全策略前视偏差审计（AUDIT_LOOKAHEAD_20260807）发现：新浪K线接口盘中实时更新当日K线，`fetch_stock_history` 无当日截断，`realtime_scanner` 每5分钟用**未完成当日K线**（high/low/close 为盘中瞬时值）生成信号。同一策略盘中触发的信号 ≠ 回测中会触发的信号 → 实盘信号无法用回测统计验证。

### 决策

- **盘中时段（<15:00）**：`_scan_single` 中 `df = df.iloc[:-1]` 剔除当日未完成K线，策略只基于已收盘历史K线判断形态
- **收盘后（≥15:00）**：完整K线可用（当日收盘价已定）
- 剔除后数据不足（<2行）返回 None，不崩溃
- 新增 `tests/unit/test_lookahead_fix.py`（4个测试）防止回归

### 理由

1. **口径一致性**：盘中信号与回测信号必须基于同一K线时点（已收盘数据）
2. **第一性原理**：信号时刻不可得的数值（盘中瞬时 high/low/close）不得参与信号判断——与断板反包前视偏差教训同源
3. **成本低**：单行修复，61+4测试通过，无回归

### 已知代价

- 盘中信号会延迟到收盘后形态确认（或盘中只看已收盘形态）——这是正确的取舍：宁可少信号，不可假信号
- P1 后续：盘中信号可标 `pending_close_confirm`，15:00 后重算确认

## ADR-022: 单实例锁 —— 杜绝双 scheduler 并行运行

**状态**: 已采纳（2026-08-05）
**影响范围**: engine/scheduler.py, utils/single_instance.py, 所有 scheduler 入口

### 背景

深度复盘 8/5 全天 11 个问题，发现 "双 scheduler 并行" 是幽灵策略/信号重复/日志混乱的根因之一。
重启操作（launchctl kickstart）可能创建新进程而旧进程未完全退出，导致两个 scheduler 实例并行运行。

### 决策

新增 `src/gugu/utils/single_instance.py` 提供文件锁机制：
- 锁文件 `data/scheduler.lock`，内容含 PID + 启动时间 + 命令行
- 获取锁时验证 PID 存活 + 命令行匹配 gugu 特征（防 PID 复用误判）
- 残留锁自动接管；进程退出自动释放
- 接入三入口：`scripts/run_scheduler.py` / `gugu.engine.scheduler._main()` / `scripts/run_live.py`
- GUGU_TEST_MODE 跳过（测试进程可并发）

### 理由

1. **数据完整性**：双 scheduler 并行写入同一心跳/信号/状态文件，导致数据竞争和文件损坏
2. **熔断绕开**：第二实例启动后熔断状态重置（risk_state.json 被覆盖），P0 防护失效
3. **信号重复**：两实例各自扫描产生重复信号通知

### 权衡

- 锁文件是软限制：`kill -9` 后锁文件残留，下次启动需清理
- 已通过 PID 存活检查 + 命令行匹配处理此场景

## ADR-023: 自动修复闭环 —— 告警不再只推送而不处理

**状态**: 已采纳（2026-08-10）
**影响范围**: health/watchdog.py, health/auto_recover.py, 全部告警响应流程

### 背景

watchdog v0.9.2 设计了 5 项健康检查 + 飞书推送，但告警到达用户时根源尚未处理。
08-10 实证：signal_history_stale 告警推送后无人处理、data_health=degraded 只被通知。
用户要求 "每次报警要分析根源，自动解决问题"。

### 决策

在 watchdog 和飞书推送之间插入自愈层 AutoRecover：

```
watchdog 5 项检查 → 有告警 → AutoRecover 根因分析 → 安全修复 → 验证
    ├─ 修复成功+验证通过 → 静默（仅审计日志）
    ├─ 修复失败 / 无法自动修 → 升级人工：飞书推送「原始告警 + 根因分析 + 已尝试动作」
```

- 修复器路由（指纹优先，防消息关键词误判）
- 安全边界：只做可逆幂等动作（重启/清理垃圾/探测）；绝不改策略配置、绝不删业务数据
- 防风暴：同指纹冷却窗口 60min + 每日上限 5 次
- 审计日志：data/auto_recover_log.jsonl 记录每次修复的完整链路

### 理由

1. **全时响应**：告警不再依赖人工，自动修复在无人值守时也能处理
2. **降低噪音**：自愈成功的告警不推送飞书，用户只看到真正需要人工干预的问题
3. **安全兜底**：所有修复动作可逆幂等，失败自动升级人工

### 参考

- `src/gugu/health/auto_recover.py` — 自动修复闭环实现（6 条安全边界）
- `scripts/health_watchdog.py` — `--auto-fix` 模式

## ADR-024: 断板反包规则单一事实源（SSoT）—— 消除三套规则漂移

**状态**: 已采纳（2026-08-12）
**影响范围**: strategies/rebound/rules.py, strategies/rebound_system.py, scripts/scan_rebound_market.py

### 背景

断板反包战法在扫描脚本（`scan_rebound_market.py`）、回测策略（`rebound_elite`、`breakout_rebound`）和策略实现（`rebound_system.py`）三处各自实现了形态判定逻辑，同一战法有三种实现版本。利柏特/联创电子误判事件暴露了规则漂移的代价：一字板判定、洗盘实体阴线要求、破位容忍线等关键规则在三处实现中各有不同。

### 决策

- 所有形态规则集中到 `src/gugu/strategies/rebound/rules.py`，作为单一事实源（SSoT）
- 扫描脚本、策略类全部引用该模块的函数
- 版本号 `RULE_VERSION = "v2.0.0-20260812"` 标识规则版本
- 5 条根源修复固化到规则函数中（一字板剔除、连板排除、实体阴线判定、破位铁律、二波异动）

### 理由

1. **消除规则漂移**：一处修改，三方同步生效，不再出现 "扫描发现但策略不判" 或反过来的情况
2. **可审计**：规则版本号 + docstring 记录每次变更的根因和日期
3. **低测试成本**：形态规则只需测试 rules.py，三方实现各自验证引用正确

### 参考

- `src/gugu/strategies/rebound/rules.py` — SSoT 规则实现
- `docs/REBOUND_FALSE_POSITIVE_FIX_20260812.md` — 误判根因修复记录

## ADR-025: 策略生命周期规范 —— 证伪三件套 + 三层架构

**状态**: 已采纳（2026-08-15）
**影响范围**: 全部策略开发流程，config/strategy_manifest.yaml, 验证方法论

### 背景

断板反包战法的完整证伪过程（事件研究 → Walk-Forward 证伪 → 截图核验修复）暴露了三个反复出现的坑：
1. 小样本 + 牛市 beta + 幸存者偏差，让负期望形态看起来能赚
2. 前视偏差让视觉评分虚高
3. 规则内部矛盾 + 实现漂移，同一战法三处实现三个版本

### 决策

将教训固化为每个策略都必须走过的硬性关卡：

**三层架构**：
- ① 认知资产层：策略验证失败后拆解出被数据验证有效的通用规则（risk_rules.py）
- ② 决策层：只跑 Walk-Forward 验证过的规则，数据当裁判
- ③ LLM 辅助层：只做提取、审计、复盘，不碰决策

**证伪三件套**（上线强制关卡）：
1. 前视偏差审计：信号与特征必须在信号时刻可得
2. Walk-Forward 样本外检验：事件研究漂亮数字 ≠ 可交易 edge
3. 真实数据核验：单元测试通过 ≠ 形态正确，必须用真实 K 线截图逐日核验

**上线门槛状态机**：
```
pending ──回测──▶ backtest_failed（证伪，永不启用）
   │
   └──样本外通过──▶ conditional_pass（有条件通过）
                      ├─ 前向验证 30+ 信号 → enabled
                      └─ 环境失效 → 降级/禁用
```

### 理由

1. **可证伪**：每个策略上线前必须经过三道关卡，任何一道不过永不启用
2. **知识沉淀**：策略验证失败不等于全盘否定，有效规则拆解为通用组件
3. **对抗性审查内建**：三件套本质是把 "事后复盘出的教训" 变成 "事前必须通过的关卡"

- `docs/STRATEGY_LIFECYCLE.md` — 完整规范文档
- `config/strategy_manifest.yaml` — `validation_gate` 字段
